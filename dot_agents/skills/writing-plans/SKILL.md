# 実装計画の作成

## 概要

エンジニアがコードベースの文脈を何も知らず、判断力に疑問があることを前提に、包括的な実装計画を作成します。タスクごとにどのファイルを触るか、コード、テスト、確認すべきドキュメント、テスト方法など、必要な情報をすべて記載します。計画全体を小さなタスクに分割して提示します。DRY、YAGNI、TDD、頻繁なコミットを原則とします。

エンジニアは熟練した開発者であることを前提としますが、ツールセットや問題領域についてはほとんど知らないものとします。良いテスト設計についてはあまり詳しくないものとします。

**開始時のアナウンス:** 「実装計画を作成するために writing-plans スキルを使用します。」

**コンテキスト:** これは専用のワークツリーで実行されるべきです（brainstorming スキルによって作成されます）。

**計画の保存先:** `docs/plans/YYYY-MM-DD-<feature-name>.md`
- （ユーザーによる計画保存場所の設定がある場合は、このデフォルトを上書きします）

## スコープチェック

仕様書が複数の独立したサブシステムをカバーしている場合、ブレインストーミングの段階でサブプロジェクト仕様書に分割されているべきです。分割されていない場合は、サブシステムごとに個別の計画に分割することを提案してください。各計画は独立して動作し、テスト可能なソフトウェアを産出するべきです。

## ファイル構成

タスクを定義する前に、作成または変更するファイルとそれぞれの責任を明確にします。ここで分解の決定が確定します。

- 明確な境界と明確に定義されたインターフェースを持つ設計単位を作成します。各ファイルは明確な責任を持つべきです。
- 一度に文脈に収められるコードについて最も良く推論でき、ファイルが集中しているときに編集がより信頼性が高くなります。大きすぎるファイルより、小さく集中したファイルを優先します。
- 一緒に変更されるファイルは一緒に配置すべきです。技術的なレイヤーではなく、責任によって分割します。
- 既存のコードベースでは、確立されたパターンに従います。コードベースが大きなファイルを使用している場合、一方的に再構成しないでください。ただし、変更するファイルが手に負えなくなっている場合は、計画に分割を含めることは合理的です。

この構成はタスクの分解に影響します。各タスクは独立して意味を成す自己完結的な変更を産出すべきです。

## 小さなタスクの粒度

**各ステップは1つのアクション（2〜5分）:**
- 「失敗するテストを書く」- ステップ
- 「失敗することを確認するために実行する」- ステップ
- 「テストをパスさせる最小限のコードを実装する」- ステップ
- 「テストを実行してパスすることを確認する」- ステップ
- 「コミットする」- ステップ

## 計画書のヘッダー

**すべての計画はこのヘッダーで始まる必要があります:**

```markdown
# [機能名] 実装計画

**目標:** [構築するものを1文で説明]

**アーキテクチャ:** [アプローチについて2〜3文]

**技術スタック:** [主要な技術/ライブラリ]

---
```

## タスク構造

````markdown
### タスク N: [コンポーネント名]

**ファイル:**
- 作成: `exact/path/to/file.py`
- 変更: `exact/path/to/existing.py:123-145`
- テスト: `tests/exact/path/to/test.py`

- [ ] **ステップ 1: 失敗するテストを書く**

```python
def test_specific_behavior():
    result = function(input)
    assert result == expected
```

- [ ] **ステップ 2: 失敗することを確認するためにテストを実行する**

実行: `pytest tests/path/test.py::test_name -v`
期待結果: "function not defined" で失敗

- [ ] **ステップ 3: 最小限の実装を書く**

```python
def function(input):
    return expected
```

- [ ] **ステップ 4: パスすることを確認するためにテストを実行する**

実行: `pytest tests/path/test.py::test_name -v`
期待結果: 成功

- [ ] **ステップ 5: コミットする**

```bash
git add tests/path/test.py src/path/file.py
git commit -m "feat: add specific feature"
```
````

## プレースホルダー禁止

各ステップにはエンジニアが必要とする実際のコンテンツが含まれている必要があります。以下は**計画の失敗**です - 絶対に書かないでください:
- "TBD", "TODO", "後で実装", "詳細を埋める"
- "適切なエラーハンドリングを追加する" / "バリデーションを追加する" / "エッジケースを処理する"
- "上記のテストを書く"（実際のテストコードなし）
- "タスク N と同様"（コードを繰り返す - エンジニアはタスクを順不同で読むかもしれません）
- コードステップにコードブロックを必要とせず、何をすべきかを説明するだけのステップ
- いずれのタスクでも定義されていない型、関数、またはメソッドへの参照

## 覚えておくこと
- 常に正確なファイルパス
- 各ステップに完全なコード - ステップがコードを変更する場合は、コードを表示する
- 期待される出力を含む正確なコマンド
- DRY、YAGNI、TDD、頻繁なコミット

## 自己レビュー

計画書を書き終えたら、新鮮な目で仕様書を見て、計画書を照合してください。これは自分で実行するチェックリストです - サブエージェントの派遣ではありません。

**1. 仕様書の網羅性:** 仕様書の各セクション/要件をざっと見てください。それを実装するタスクを指摘できますか？ 欠落がある場合はリストアップしてください。

**2. プレースホルダースキャン:** 計画書を検索して、上記の「プレースホルダー禁止」セクションのパターンのいずれかがないか確認してください。あれば修正してください。

**3. 型の一貫性:** 後のタスクで使用した型、メソッドシグネチャ、プロパティ名は、以前のタスクで定義したものと一致していますか？ タスク3で `clearLayers()` と呼ばれる関数がタスク7で `clearFullLayers()` と呼ばれるのはバグです。

問題を見つけた場合は、インラインで修正してください。再レビューする必要はありません - 修正して先に進んでください。タスクがない仕様書の要件を見つけた場合は、タスクを追加してください。

## 実行の引き継ぎ

計画書を保存した後、実行方法の選択肢を提示します:

**「計画書が完成し、`docs/plans/<filename>.md` に保存されました。2つの実行オプションがあります:**

**1. サブエージェント駆動（推奨）** - タスクごとに新しいサブエージェントを派遣し、タスク間でレビューし、高速なイテレーション

**2. インライン実行** - このセッションで executing-plans を使用してタスクを実行し、チェックポイントを伴うバッチ実行

**どちらのアプローチを選びますか？」**

**サブエージェント駆動が選ばれた場合:**
- **必要なサブスキル:** subagent-driven-development を使用
- タスクごとの新しいサブエージェント + 2段階レビュー

**インライン実行が選ばれた場合:**
- **必要なサブスキル:** executing-plans を使用
- レビューのためのチェックポイントを伴うバッチ実行
