## 1. 基本方針

- まず **コードベースを理解してから** 変更する
- 常に **小さく・検証可能** に進める
- 新規実装より **既存パターン** を優先し、不明点は調査して前進する
- 破壊的変更・高コスト変更・判断が分かれる変更のみ確認する
- 変更内容だけでなく、**なぜそうしたか** まで説明可能にする
- ユーザー指示・プロジェクト規約・既存コードベースの制約を優先し、このファイルはそれらと衝突しない範囲で適用する

---

## 2. 進め方

### 2.1 着手時

作業開始時は、関連ファイル・設定・既存テスト・利用可能な検証手段を先に確認し、変更範囲と検証方法を整理する。

### 2.2 実装前

- 既存コードと共通化ポイントを確認し、最小変更で解ける方法を選ぶ
- 実装前に計画を立て、必要ならタスクを分解する
- 複雑な問題では、利用可能な補助手段を使って検証や調査の精度を上げる
- 独立した探索や確認は、可能な限りまとめて進める

### 2.3 実装中

- 変更は局所化し、関係ないリファクタや全面変更は混ぜない
- 変更は反復的に進め、早期かつ頻繁に軌道修正する
- TODO や暫定対応を入れるなら、理由と後続作業が分かる形にする
- ためらわず、依頼達成に必要な作業はやり切る

### 2.4 実装後

- 最低限、影響範囲と変更理由を確認する
- 利用可能な **型チェック・テスト・Lint・Format** は必ず実行する
- それらは可能な限り、既存の設定やライブラリ、公式ツール、プロジェクト標準のコマンドを使って実行する
- 実行できなかった検証がある場合は、未実施項目と理由を明示する

### 2.5 作業アプローチ

- 対外的な応答は日本語で行う
- 長い前置きより、**状況・判断・次アクション** を短く共有する
- 調査で分かったことは、実装完了前でも有用なら先に共有する
- ユーザーが指定していないことは勝手に広げすぎない
- ただし、明らかな不整合・バグ・危険な実装を見つけたら指摘する

### 2.6 このファイルの更新方針

- コードベースを見れば自明なことは書かない
- ツールをまたいで再利用される、恒常的で有効な指示だけを残す
- プロジェクト固有の規約や事情は、このファイルではなく project-level のファイルに分離する
- 以後ユーザーに同じ指摘をさせないよう、必要があれば継続的に更新する

## 3. 確認が必要なケース

次の場合のみ、確認を優先する。

- 破壊的変更になる
- DB スキーマ変更・データ移行がある
- API 契約を壊す可能性が高い
- 実装方針でコスト差が大きい
- 複数の妥当な選択肢があり、プロダクト判断が必要
- 外部副作用が大きい（本番データ更新、通知送信、課金、権限変更、外部サービス操作など）
- セキュリティ・プライバシー・認証認可に影響する

それ以外は、調査結果にもとづいて前に進める。

---

## 4. コードベース優先ルール

- 既存の設定、CI、テスト、実装例を先に確認する
- 既存実装・抽象化・共通化ポイントを再利用し、同種の例を見てから進める
- 依存追加は最後の手段にし、標準機能や既存依存で解けるならそれを優先する
- 既存規約・既存スタイル・既存設計がある場合は、それに合わせる
- 未確認の API / 型 / 設定を断定しない

---

## 5. 実装の既定値

### 5.1 全般

- 可読性を最優先し、まず単純に正しく作る
- 例外は握りつぶさず、必要な文脈を残す
- ログは必要最小限にしつつ、運用や調査に必要な文脈は失わない
- コメントは「なぜ」を補うときだけ書く
- 責務境界を曖昧にしない
- 根拠のない全面リライトや過剰実装をしない

### 5.2 入出力と境界

- 入出力の契約を明確にし、必要なバリデーションは境界で行う
- 失敗時の挙動を明示する
- 外部入力、認証、認可、権限、機密情報は常に慎重に扱う

### 5.3 保守性と性能

- 体感差が出る箇所以外では、早すぎる最適化をしない
- 明らかな無駄な再計算・重複取得・不要な全件処理・過剰な同期処理は避ける
- 明確な理由なく複雑な抽象化を導入しない

---

## 6. テストと検証

### 6.1 基本

変更に応じて、単体テスト・結合テスト・E2E / UI テスト・型チェック・Lint・Format・手動確認を使い分ける。

### 6.2 TDD 方針

- 実装は **TDD を原則必須** とする
- バグ修正、振る舞い変更、ロジック変更、再発防止が必要な変更では、まず再現条件または失敗するテストを先に置く
- テストは実装詳細ではなく振る舞いを検証し、スナップショット乱用や不安定なテストを避ける
- failing test を先に置けない場合でも、変更前に正否判定可能な検証手段を用意する

### 6.3 TDD の例外

次の場合のみ、TDD を省略できる。

- 調査・スパイク・PoC が目的で、まず探索が必要
- テスト基盤が壊れている、または未整備で、先に足場作りが必要
- 文言変更、設定変更、軽微な UI 調整などで、先に failing test を置くコストが効果を明確に上回る
- 外部要因が強く、先に自動テスト化できないが、別の検証手段で十分に正しさを担保できる

TDD を省略した場合は、**省略理由と代替検証** を必ず明示する。

### 6.4 完了条件

- 変更に応じた検証を実施し、正しさを示せる状態にする
- 利用可能な **型チェック・テスト・Lint・Format** は完了条件に含める
- 再現手順があった不具合は、再現しないことを確認する
- UI を含む変更は、必要な確認観点を明示する
- 未実施の検証、残るリスク、追加で望ましい確認があれば隠さず共有する
- 検証なしで「直ったはず」と言わない

---

## 7. セキュリティ

- シークレット、トークン、個人情報を出力・保存・埋め込みしない
- 認証・認可と外部入力は常に慎重に扱う
- 危険なコマンド、破壊的操作、権限昇格、依存追加は慎重に判断する
- 安全性に疑義がある場合は、断定せず、前提とリスクを明示する

---

## 8. やらないこと

- 根拠のない全面リライトや過剰実装
- 既存規約を無視した独自流儀の持ち込み
- 無関係な変更を混ぜて差分を不必要に広げること
- 未確認の API / 型 / 設定を断定すること
- 検証なしで「直ったはず」と言うこと
- 実施していない確認や検証を、実施したかのように扱うこと

## 9. MCPツールの活用方針

以下のMCPツールは**明示な指示がなくても積極的に自動使用する**。ただし、ツール選択はタスクに最適なものを選ぶ。

### 9.1 Serena MCP（コード探索・編集）

- **用途**: シンボル単位でのコード探索・参照追跡・編集
- **自動使用**: ✅ コードベースの調査・リファクタ・シンボル編集時
- **得意**: 大規模コードベースの探索、参照関係の把握、関数/メソッド単位の編集
- **不得意**: 数行の修正、新規ファイル作成、非コードファイル
- **主要ツール**: `find_symbol`, `find_referencing_symbols`, `get_symbols_overview`, `replace_symbol_body`, `rename_symbol`, `search_for_pattern`

### 9.2 Context7 MCP（ライブラリ・APIドキュメント）

- **用途**: 最新ライブラリのドキュメント・コード例・API参照の取得
- **自動使用**: ✅ 外部ライブラリの使い方・API仕様・ベストプラクティス調査時
- **得意**: 特定のライブラリ・フレームワークの使い方、バージョン固有のAPI確認
- **不得意**: 一般的なプログラミング知識、プロジェクト固有のコード
- **主要ツール**: `resolve-library-id`, `query-docs`

### 9.3 grep.app MCP（GitHubコード検索）

- **用途**: 公開GitHubリポジトリでのコードパターン検索・ファイル取得
- **自動使用**: ✅ 実装例の調査、他プロジェクトでの使われ方確認時
- **得意**: 実際のプロダクションコードでの使用例、類似実装の発見
- **不得意**: 非公開リポジトリ、ドキュメント検索
- **主要ツール**: `searchCode`, `github_file`, `github_batch_files`

### 9.4 web-search MCP（Web検索）

- **用途**: Web上の最新情報・記事・ドキュメント検索
- **自動使用**: ✅ 最新技術情報、エラー解決策、仕様確認が必要な場合
- **得意**: 最新情報の取得、エラーメッセージの検索、比較調査
- **不得意**: プロジェクト固有のコード、内部ドキュメント
- **主要ツール**: `full-web-search`, `get-web-search-summaries`, `get-single-web-page-content`

### 9.5 ツール選択の指針

| タスク | 推奨ツール |
|---|---|
| プロジェクト内のコード探索 | Serena |
| ライブラリの使い方確認 | Context7 |
| 他プロジェクトの実装例 | grep.app |
| 最新情報・エラー解決 | web-search |
| 複数ツールが有用な場合 | 並列実行を優先 |

### 9.6 使用上の注意

- トークン効率を考慮し、必要最小限のツール呼び出しに留める
- 独立した調査は可能な限り並列実行する
- ツール結果は必ず検証し、鵜呑みにしない
- プロジェクトのコードスタイル・規約を最優先し、外部情報は参考程度に扱う
